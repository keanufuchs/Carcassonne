Architektur & Design

Schichten · Domänenmodell · Entscheidungen

Architektur

Strikte 4-Schichten-Architektur

Electron
App-Lifecycle, Desktop-Fenster
UI · React + CSS / Three.js
nur Rendering
Controller
Befehle + Pub/Sub
Core · reines TypeScript
Regeln, State, Scoring
Leitprinzip

Jede Schicht importiert nur von darunter — keine Vermischung der Belange.

  • Kern framework-unabhängig
  • testbar ohne Browser/DOM
  • 2D ↔ 3D, Web ↔ Desktop ohne Logik-Änderung

→ Wo diese Schichten im Code liegen: nächste Folie (Pflichtfrage 3).

Pflichtfrage 3 · Code-Einstieg?

Dieselben Schichten — konkret im Code

Einstieg: electron/main.ts → src/App.tsx. Jede Schicht hat ihren festen Ort im Repository.

Schicht → Datei
  • Electron electron/main.ts
  • UI App.tsx · BoardView.tsx
  • Controller GameController.ts
  • Core Game.ts · GameState.ts
„Wie geht es weiter?"
  • Spiellogik lesen → GameState.ts → Game.ts
  • Wertung ändern → core/scoring/
  • KI verbessern → ai/heuristic | intelligent
  • Regel-Test ergänzen → tests/scenarios/*.yaml
Design

Domänenmodell: ein zentraler GameState

Kernidee
  • Ein zentraler GameState
  • Fortschreibung per reiner Funktionen — keine verstreuten Mutationen

GameState → Board → Feature → MeeplePlacement

Schlüssel-Entscheidung

Meeples leben am Feature — nicht an der Kachel oder im globalen State.

  • „Wem gehört ein Gebiet?" ist lokal
  • korrektes Merging beim Anlegen
  • einfache Mehrheitswertung
Design

Spielzug als Zustandsautomat

PLACING_TILE
Kachel ziehen, drehen, legen
→
PLACING_MEEPLE
Meeple setzen / überspringen
→
nächster Spieler
zurück zu PLACING_TILE
→
GAME_OVER
Endabrechnung

Controller erlaubt nur phasen-gültige Befehle → ausschließlich regelkonforme Züge.

Design

Zentrale Entscheidungen — begründet

Entscheidung Begründung
Framework-freier Core testbar ohne DOM; wiederverwendbar in Web/Desktop/Server/KI
Reine Funktionen (state) → Result deterministisch, leicht serialisierbar/persistierbar
Feature-Graph (Union/Merge) inkrementell & effizient — Gebiete wachsen lokal
Client-Server statt P2P autoritatives Backend = einfache Sync, weniger Cheating
KI über MCP-Tool-Use strukturierte Analyse → bessere, nachvollziehbare Züge
Datengesteuerte Kacheln Wartbarkeit — Verteilung als Daten, nicht hartkodiert

Implementierung

Spielkern & Wertung

canPlace: Kanten müssen passen — Straße trifft Straße, Stadt trifft Stadt, Wiese trifft Wiese.
Spielkern (reine Funktionen)
  • 72-Kachel-Deck — datengesteuert
  • canPlace — Nachbar + Kantenmatch
  • Feature-Merge — Union-Find-Semantik
  • Completion — fertige Gebiete erkennen
Wertung
  • mid-game — Straße/Stadt/Kloster bei Abschluss
  • end-game — unvollständige Gebiete
  • Wiesen — 3 Pkt je fertige Stadt
  • Mehrheit — meiste Meeples gewinnen
Erweiterung EW-01

Netzwerk-Multiplayer — autoritatives Backend

Server
  • REST-API — erstellen, beitreten, Aktion
  • WebSocket — Echtzeit-Broadcast (Port 3001)
  • Polling-Fallback ohne WebSocket
  • Persistenz — Beitritt per Code, Reconnect
Kernprinzip

Der Server validiert jede Aktion über denselben Core wie der Client — eine Regel-Implementierung, kein Duplikat.

Erweiterung EW-02

Reasoning AI — drei Stufen, mit Fallback

Zufall
zufälliger legaler Zug
·
Heuristik
Greedy, ohne API-Key
·
Reasoning AI
LLM + MCP-Tool-Use
LLM ruft Analyse-Tools (MCP)
  • list_legal_moves
  • get_board_features
  • get_player_status
Robustheit (US-A3)

Kein Key, Timeout oder ungültiger Zug → automatischer Fallback auf Heuristik. Kein Absturz.
